# 上传书籍后匹配豆瓣评分：技术调研

调研日期：2026-10-30（Asia/Shanghai）。本轮只做代码审查和公开资料调研，未接入评分服务、未更改线上数据、未调用付费模型。

## 结论

可以设计准确、可解释的匹配流程，但不能承诺任意文件都能全自动获得正确、实时的豆瓣评分。必须同时解决：

1. 文件对应哪个作品、语言、译本、出版版本和分册；
2. 对应哪个豆瓣 subject；
3. 能否持续、获授权地取得该 subject 的评分及评价人数。

推荐：元数据与版权页识别 → ISBN 优先召回 → 版本核验 → 高置信度自动关联 / 歧义由用户确认 → 授权评分来源 → 缓存与定期刷新。无法核验时留空，不用模型猜评分，不用同名热门版本代替。

商业数据接入是独立前提。豆瓣现行法律声明“二、信息和数据”明确提到条目信息、评分、评价数量及商业产品中的展示，并提供 bd-team@douban.com 授权联系渠道。这是来源方的使用条件，不是本报告对个案法律责任的判定。[1]

## 已核实的项目现状

- `worker/src/routes/books.ts`：上传 EPUB 至 R2，插入 books 记录，异步触发 parse；接受的文件标题可能只是文件名。
- `worker/src/pipeline/epub.ts`：ParsedEpub 返回 title、author、language、description、toc、chapters、cover；未提取 ISBN、出版社、出版日期、译者和版本。后端 author 目前只取第一个 creator。
- `web/src/book/epub.ts`：客户端读取 title、多个 creator、language，但没有建立版本识别信息。
- `worker/migrations/0001_init.sql`：books 无 ISBN、外部条目关联或评分快照字段。
- `worker/src/pipeline/index.ts`：已有 parse/embed 异步任务及费用计量。新增评分任务应与阅读就绪状态隔离，不能因第三方查询失败把正常书籍标记为 failed，也不能为补 ISBN 重新做 embedding。

## 来源与接入路线

| 路线 | 能解决的问题 | 判断 |
| --- | --- | --- |
| 豆瓣直接授权的数据服务 | 条目搜索、版本信息、评分、人数、刷新与展示权限 | SaaS 首选；接口供应、申请条件、报价、配额、缓存期限仍待商务确认，不能保证一定获得 |
| 有可核验授权链的供应商 | 代为提供条目与评分 | 备选；要求证明数据来源、展示/缓存/转授权范围、更新时间、错误语义和 SLA；本轮未核实到可推荐的具体供应商 |
| 抓取豆瓣公开页面 | 页面可访问时可能解析评分 | 不作为正式服务基础；需先解决使用授权，并验证页面变化、访问限制、验证码、可用性。不能靠轮换代理/用户 cookie 维持功能 |
| 搜索服务 | 通过 ISBN / 书名作者发现候选 subject URL | 仅作候选发现；摘要可能陈旧、缺版本信息，不作为最终评分证据。搜索服务本身也可能收费 |
| 用户粘贴豆瓣条目链接 | 人工解决对应条目歧义 | 值得提供；链接不能解决后台评分读取权限或新鲜度，用户关联仅作用于其自己的书籍 |
| Google Books / Open Library | ISBN 查询、补充作者/出版社等书目元数据 | 可作辅助，不能把其评分当成豆瓣评分；中文覆盖率需实测，分别遵守各自条款 [6][7] |

豆瓣官方 GitHub 仍保留历史 API 客户端，但历史代码不是当前服务承诺。[5] 本次无法访问旧开发者文档，也未核实到当前可自助申请、可直接用于本 SaaS 的公开图书 API。不能据此断言所有授权 API 都不存在。

检索到的 calibre-douban 维护者也提示使用自己的 API key 或申请授权，可作接入风险的工程旁证，不视为豆瓣官方政策。[8]

## 文件识别：先辨认版本

### 元数据优先，不依赖格式

建立统一 BibliographicIdentity，格式解析器只负责产生候选与出处：

- 原始书名、规范化书名、副标题、原作名；规范化不能删掉卷次、修订版、节译等重要差异。
- 全部作者及角色、译者、语言、出版社/品牌、出版日期、版次、卷次。
- identifiers 数组：scheme、原值、规范值、来源位置、角色（本电子版 / 来源纸本 / 套装 / 分册 / 未知）。
- 已有豆瓣 subject ID（若文件包含）只作候选，必须核验；上传文件可含过时或错误信息。
- 原始证据和冲突记录，不把推断值覆盖成已核验事实。

EPUB 先读 OPF 的 dc:identifier、dc:source、creator/contributor 与角色、publisher、date、language；兼容 EPUB 2 属性和 EPUB 3 refinements。W3C 明确 dc:identifier 也可能是 UUID、DOI，不能把任意数字标识当作 ISBN。[2]

缺失时识别目录/书脊中的版权页、出版说明、书名页，提取带上下文的 ISBN；不要无差别扫描全文后取第一个号码，参考文献和广告页会出现其他书的 ISBN。版权页不一定只在最前几页，需结合标题与结构定位。

后续 PDF：优先文本层与元数据，扫描件只对候选版权页 OCR；TXT 等无可靠版次时允许未知。OCR/模型仅辅助提取可回查的原文证据，不生成 ISBN、出版信息或评分。

### ISBN 处理

- 去掉 ISBN 前缀、空格、连字符，规范全角字符；保留原值。
- 校验 ISBN-10/13 校验位；ISBN-10 可规范化至对应 978 ISBN-13。不能把所有 13 位号码当 ISBN，也不能给 979 ISBN 强行生成 ISBN-10。
- 校验位通过只说明号码结构有效，不代表号码确实属于这本书。
- 多个 ISBN 不互相覆盖；电子版、纸本、套装与分册分开保存。
- 国际 ISBN 机构说明，不同版本、语言和产品形式应独立标识。因此电子版 ISBN 在豆瓣查不到，不能直接判定该作品不存在。[3]

## 匹配与决策规则

候选来源按可靠性组合：已有且核验过的关联、有效 ISBN 检索、明确来源纸本 ISBN、书名 + 作者 + 译者/出版社检索。封面仅辅助，不能因为图片相似就认定版本一致。

| 证据 | 默认行为 |
| --- | --- |
| 本版 ISBN 精确一致，书名/作者无明显冲突，候选唯一 | 自动关联 exact_edition |
| 明确标注的来源纸本 ISBN 一致，其他出版信息一致 | 可关联 source_print_edition，显示“对应纸质版” |
| 同书名、作者、译者、出版社/版次一致，但没有可靠 ISBN | 提供高相关候选；第一版保守要求确认 |
| 同作品但译者、修订版、分册、语言或出版信息冲突 | 不自动关联；明确提示差异 |
| 仅书名匹配，或多个近似候选 | 显示少量候选供确认，不取第一个/最高分/最多人评价的条目 |
| 没有可靠候选 | 未匹配；允许补充信息或粘贴链接 |

用规则产生 matchKind 与 evidence，不把人为加权分数包装成“99% 正确概率”。后续可用标注样本校准阈值。

实际例子：豆瓣有马振骋译、人民文学出版社、ISBN 9787020042494 的《小王子》，也有胡雨苏译、中国友谊出版公司、ISBN 9787505715660 的版本。它们属于不同 subject，应分别关联。[4a][4b] 本轮搜索快照也展示不同评分和人数，但不将快照数字当作当前实时值。

## 评分读取与产品表现

评分记录至少包含 provider、subjectId、canonicalUrl、rating（可空）、ratingCount（可空）、fetchedAt、providerUpdatedAt（如提供）、sourceVersion。匹配记录另外保存 matchKind、evidence、confirmedByUser、resolverVersion。

建议区分以下状态：

- 待查询 / 匹配中；
- 需确认版本；
- 已关联且有评分；
- 已关联但豆瓣尚无评分（null，不是 0 分）；
- 未找到条目；
- 来源暂不可用；
- 缓存评分已过期。

页面可以显示“豆瓣 8.7 · 1,234 人评价”，点击查看来源及版本；这是示意数字。若展示的是来源纸本，另标“对应纸质版”。提供“匹配有误”入口。不得把访问失败写成“暂无评分”，也不在缓存过期后显示“实时”。

若授权来源返回网页而非结构化 API，可评估结构化数据与 DOM 的双路径解析，核对 subject、书名、ISBN、评分范围及人数；本轮没有成功读取豆瓣原始页面 HTML，尚未验证其当前 JSON-LD/DOM 结构，不能承诺具体选择器可用。

## 在 Cloudflare 架构中落地

建议增加独立任务 `resolve_book_rating`，在 EPUB 解析完成后调度，不阻塞上传、阅读或 embedding。任务有独立状态、限时、幂等 key、重试退避；429/鉴权错误/验证码等按来源协议处理，不能无上限重试。

概念数据表（尚未迁移）：

- book_bibliography：每本私有文件的候选书目及出处；
- book_external_matches：用户书籍 → 来源 subject，含版本关系和用户确认；
- external_book_subjects：来源公开条目元数据；
- external_rating_snapshots：按来源 + subject 保存评分、人数、抓取时间；
- metadata_lookup_jobs / usage：去重锁、任务结果、请求量和费用。

共享公开条目缓存可减少重复查询，前提是来源合同允许；用户上传文件、私有解析证据和用户手工选择不能被混入全局自动匹配证据。用户 A 的错误确认不应污染用户 B。

缓存默认策略建议（最终以授权条件为准）：普通条目约 7 天、近期热门/新书约 1 天；优先刷新近期被查看的条目。映射较稳定，评分需刷新。未找到与临时错误分别设置短期缓存，成功旧值在刷新失败时保留并标时间。请求合并避免同时上传同一本书重复收费。

现有书籍可从 R2 原文件补做 metadata-only 回填，无须重建 chunks / embedding；仅后台元数据变化，不能移动原文偏移或使旧划线失效。

粘贴链接只接受规范的 book.douban.com/subject/<数字>/，提取 ID 后由固定 provider endpoint 查询；不开放任意 URL 服务器抓取。第三方只需 ISBN/书目查询，不应发送整本电子书、用户身份或笔记。

## 费用与验证

普通 EPUB 识别和规则匹配不需要 LLM，AI token 为 0。外部查询、OCR、少量疑难识别模型和 Workers/D1/Queue 各自记账；缓存命中单列。授权报价和供应商价格本轮未取得，不能给出可信的每本金额。

增量成本可按以下公式估算：

`缓存未命中的检索数 × 检索单价 + 条目读取数 × 读取单价 + 刷新数 × 单价 + OCR/模型实际用量 + 基础设施增量`

费用 debug 中建议展示 `书籍元数据解析`、`豆瓣候选查询`、`豆瓣评分读取/刷新`、`版权页 OCR（若使用）`，每项带请求数、缓存命中、结果、实际 token 与价格来源；未知报价显示未知，不伪记为免费。

先做约 100–200 本的标注验证集，覆盖微信读书导出、无 ISBN、错误 ISBN、同名书、多个译本、简繁版、不同卷次/合集、重排版、电子/纸本 ISBN 不同、新书无分、来源不可用等。这个样本用于初步发现问题，不足以证明极高准确率。

分别衡量：自动匹配 precision（可设 99% 为产品目标，但不是已验证结果）、自动匹配覆盖率、人工确认率、可取分比例、评分时间差、请求失败率、每本增量成本。不能只报“查到多少本”而隐藏匹配错版。

推荐第一阶段完成身份解析、版本匹配和人工纠错；同时核实授权数据渠道。授权确认后接入评分与缓存。如果尚无可用来源，产品先提供关联/跳转豆瓣，不展示无法核验的分数。
